# Architecture

[North star](NORTH_STAR.md) defines the product. This page distinguishes the intended active loop from the capabilities at committed HEAD; [current state](CURRENT_STATE.md) is the implementation ledger.

## Ownership and data flow

1. A case receives a user symptom and a bounded parallel baseline of registered, typed, read-only Windows probes. Each result is persisted with stable identity, source-observation and capture times, provenance, redaction, quality, limitations, and coverage. Case-open and audit times are distinct. Explicit process/application wording routes to the registered application snapshot. Its saved source holds at most 512 processes; the downstream 64-candidate menu keeps 48 low-PID and 16 recent instances. Both retain exact creation identity and report omitted coverage. A recent process can still fall outside these bounds, and a compact case report can show fewer rows than the saved evidence. An exact standalone executable name can bind only when the complete saved table identifies one process; the subsequent CPU sample rechecks PID and creation identity. A bounded exact-name excerpt carries positive rows or a complete-table absence and the target CPU sample into the reasoning view, with observation times and limits.
   A typed affected-task report can preserve the user's action, target hint, expected result, and reported result. The report remains unverified; target identity and task outcome require independent observations.
   A synthetic task-observation reference can bind one executed `fixture.task_baseline` record to a case, source, collector execution, record hash, exact UTC window, and explicit synthetic limitation. The owner rereads that custody before assembling a version-2 frontier request and again before a ranked measurement can be selected or linked to execution. Laya carries the complete bounded task context as one required worker-state field across candidate comparisons; local-deep ranking receives the same typed content. An invalid binding is quarantined with a visible gap. This synthetic transport contract does not verify a real user task or authorize a probe.
   The `task.loopback_http` observer executes one GET against an exact `127.0.0.1` high port and nonce health path. A normal user can supply one fixed-shape URL in the desktop problem description; the earlier opt-in test-owned entry remains separate. It has no general URL, redirect, proxy, DNS, retry, or model-provided target. Its source record, probe execution, times, response status and exact reported-action digest must agree before a case can call it an exact-action replay. This verifies that replay's result, not a historical report or application cause. The private controlled-trial owner creates, faults, restores and removes only its disposable service; the investigator itself remains read-only toward Windows.
2. The deterministic coordinator forms a changing frontier of existing evidence retrieval, case-evidence graph traversal, reference-mechanism branches, precise new measurements, and deep-reasoner escalation. Candidate identity binds kind, target, registered parameters, source and observation window. A later window may justify a repeat; an identical in-flight candidate must not be duplicated.
   A small SCOUT lookahead may preview one cheap registered probe related to the baseline through sourced relationships. Runtime discovery declarations include observable, output/unit hints, target/parameter/window shape, cost, resources, privacy/effects, and purpose; discovery only filters the menu and never grants execution authority. All existing built-in probes declare bounded discovery metadata; speculation remains subordinate to demanded work.
3. The fast advisory provider repeatedly ranks bounded structured batches from the affected frontier. Persistence invalidates only dependent candidates; microbatches avoid a full re-rank. Admission checks source generations, state, deadlines, budgets, resource classes, catalog costs, permissions, and durable one-shot identity. Unrelated probes and deep reasoning must not block an admitted follow-up.
   A comparison-only local-deep policy (`38a3909`) uses the same frozen frontier request and source revalidation, with one owned pinned Qwen client for probe advice, ordering, and reasoning. It may return only a complete permutation of offered IDs; malformed, incomplete, unfit, and late rankings abstain to the existing order. Its bounded longer ranking turn is charged to the same case/session deadline. No Laya worker presentation or training sample is claimed for this policy; default product routing remains deterministic unless explicitly opted in.
4. The deep advisory provider receives a focused, cited evidence map, maintains competing hypotheses, requests distinguishing evidence, and can redirect the fast provider. It cannot turn its explanation into a fact or an executable command. Deterministic code decides whether a proposed diagnosis is supported or explicitly unresolved.
   At `f60df93`, an exact batch selected by the last applied asynchronous deep response may collect before the next deep review when its total registered cost estimate is at most ten percent of the remaining case time. The gate verifies pending proposal identity, source request and proposal hashes, current manifest and capability; it does not grant execution authority. Adaptive fast follow-ups and escalation remain active. A private run-owner marker retains the batch's new execution and evidence IDs, including failed coverage, so an early partial-source review does not silently satisfy the terminal review. At idle or final closure, the coordinator may make one bounded terminal-state attempt and checks exact frozen request/read-set inclusion, not generation alone. Newly eligible advice resumes normal routing only within the original round, probe and time limits. Cancelled cases do not start this review. Rejected or context-limited attempts do not trigger indefinite retries. Cost is a heuristic: an unexpectedly slow eligible collector can delay the next deep review until terminal state or the deadline. Input inclusion does not prove fitted-model visibility or correct reasoning; actual-model qualification remains separate.
   At `b69c24a`, idle handling settles that exact terminal attempt before considering another deep request. A changed advisory hypothesis alone does not repeat an already reviewed terminal batch. New evidence generations, requested facts or catalog work, and later validated focus-delivery receipts for omitted older evidence remain eligible for review. Ordinary bounded fitting omissions do not count as new observations. Supported closure and cancellation retain precedence over another collection round.
   At `62199d9`, idle handling retains the exact spent terminal task across queued no-new-fact turns. The token is private to the current run, bound to the current last deep admission and same case, and reset by a new coalesced batch or run boundary. It does not label a rejected attempt accepted. New generations, requested detail/catalog work, later validated focus, and explicit fast questions retain their existing paths.
   At `b93ede5`, an earlier collecting-epoch request can satisfy that terminal attempt when it already contains every final observed record. The coordinator verifies each exact execution is `ok` and nonempty, each typed observed fact belongs to the same case and collector/version/execution, and the frozen request and read-set contain the complete terminal ID set with unchanged row hashes. Saving the later `collected` checkpoint alone does not require another review. Failed executions, coverage records, missing rows, changed facts and partial input retain the stricter fallback. This is an input-coverage optimization, not evidence of correct model interpretation.
   If a successful observation arrives after the last frozen deep task, the coordinator may freeze one further review before idle closure, bounded by the case deadline, rounds and evidence generation. The mixed frontier offers only source-bound, registered read-only measurements: process target pressure from a valid application inventory, host pressure and storage from `core.resources`, GPU telemetry from `local_ai.snapshot`, and network configuration from `network.connectivity`. Exact named-process CPU and liveness cases filter irrelevant measurements in the streaming, general, and event-driven admission paths; existing broader cases retain their catalog. Each selected candidate still needs exact admission and execution; other registered follow-ups use their separate admission path. Missing process inventory removes that candidate and records a gap without aborting otherwise valid mixed items.
   SQLite schema 38 adds an immutable `deep_proposal_execution_links` row only when an applied, nondegraded asynchronous deep proposal survives coordinator selection and the exact registered invocation, manifest and observed execution are committed together. The row binds the source request and proposal hashes, accepted and selected state versions, plan instance, execution, probe, manifest, target, parameters and window. A merely matching probe ID or later run is not deep-origin proof; old databases and synchronous proposals have no retroactively invented link. Writer and scorer verify the complete case audit chain and the exact execution plan, case, probe, outcome, finish time and parameter digest, in addition to the applied mailbox, checkpoint, registry and execution. Runtime commits the probe audit before the optional origin receipt within the same transaction; absent, empty or mismatched plan identity cannot earn credit. This custody says what led to a run, not whether the result supports a cause.
   For an exactly bound synthetic task, a version-5 reasoning request carries its validated task observation and only selected sources backed by durable focus receipts. Event, synchronous, and mixed PDF frontier deliveries commit the receipt with the case checkpoint; the coordinator also reserves the task and selected evidence in the bounded brief. Fixture source coverage names target/window applicability, not cause. Ordinary catalog attention has no frontier focus receipt and does not gain a selected-source marker from this contract.
   For the exact loopback question, Laya can select a source-bound registered `network.listeners` measurement after the product-owned GET. After a timeout, exactly one later matching listener row with an available PID and creation identity can admit `network.listener_owner_pressure` through the mixed candidate registry. Its isolated worker repeats only the same exact GET while identity-checking and sampling that owner; it records overlap, HTTP outcome, CPU in logical-core units, and process-level limits. The candidate is absent from the generic capability menu, and admission rechecks the case, source, target handle, PID, birth time, port and nonce. Sol waits until the useful source-bound check is attempted, avoiding a preliminary review that lacks the discriminating result. Closure requires an applied response that considered every decisive observation and used the task, recurrence and any successful owner-pressure observation. Listener use may be covered by that later owner replay only when persisted execution parameters match the trusted PID, creation time, port and nonce, and both replay-boundary ownership checks are valid. Missing or invalid ownership proof retains the original listener-use requirement. The coordinator rereads source and execution custody; a concurrent process sample can favor active work or weaken CPU saturation but cannot prove which request handler ran. Broad host probes remain excluded from this narrow scope. The earlier GET, later listener, and repeated GET retain distinct times. Terminal execution receipts, not duplicate-prevention reservations, determine when inventory/listener collection is ready for review. Narrow present-time named-process questions can await the existing applied deep response and close after it considers and uses the complete source-custodied inventory; causal questions, incomplete tables and unresolved requested details cannot use this closure. The same deterministic sampled-state assessment is available to Basic, and its evidence does not establish a cause or earn model-selected-check credit.
   Registered `application.target_pressure` version 2 records the logical processor count and both CPU units in the same identity-bound observation: percent of total logical-processor capacity and CPU seconds per elapsed second (logical cores). One busy core on a 24-processor machine is about 4.167 percent, not evidence of negligible target work. Schema validation requires consistent units; older observations remain readable without invented core usage. Basic and model providers receive the same facts, and neither unit proves responsiveness or a cause.
   A categorical prediction is stamped when accepted. A later exact current-case probe fact may mark that advisory hypothesis contested after source and time revalidation; a matching fact alone does not prove its cause. The coalesced collection path reconciles those predictions immediately after collection and before the next deep response can update a rival. Both synchronous and concurrent deep paths retain model claims as advisory.
   Reasoning request v6 separates exact, finite prediction output contracts from discovery hints. Only a registered probe version can supply top-level fact names and typed allowed values; finite declared outputs are checked on successful probe results. The whole request is bounded to 16 outputs and 64 values. Prompt fitting pages optional graph, unseen catalog and reference context before it omits the complete registered output menu; it still omits that menu before evicting focused observations. The local deep provider rejects predictions outside the menu that actually survived fitting, including after its bounded retry; the shared validator also rejects new predictions for completed probes. The coordinator checks the original registered contract and stamps the probe version. Later contradiction requires the same trusted collector version; a same-ID advisory statement revision cannot reclassify an existing contradiction as support or missing evidence. Empty or omitted output domains cannot support a categorical expected fact. Older request versions retain their prior serialization and prompt behavior.
   Request v7 and response v4 optionally permit an explicit same-ID statement revision that retires specified old support citations. The coordinator supplies the digest of each complete prior hypothesis; the provider must name that digest and the retired IDs, and those IDs and the prior row must survive the fitted provider view. A changed statement also needs genuinely new visible support or counterevidence. All prior contradictions and missing citations remain, while predictions and their observation boundary stay unchanged. Invalid or absent intent leaves the older rival retained. An accepted asynchronous revision writes an immutable step link with the prior and revised hashes, retired IDs and source request hash in the same checkpoint transaction; storage verifies the applied deep response and prior row again. Synchronous requests do not advertise this capability and reject unsolicited intents. Additive fields keep older request and mailbox records readable. This records citation history rather than silently treating retired support as current support; it does not establish the new statement as true.
   Response v5 optionally records at most two typed noncausal reviews of newly observed evidence when a prior rival is presented. Each review gives a bounded disposition and explanation; it adds no causal support or execution authority. An `unavailable` missing-evidence acknowledgment requires the typed source observation to establish unavailable collection, not just model prose. The Structured provider offers exact recent IDs that survived prompt fitting and derives visible prior IDs from that fitted packet. A custom provider's visibility fields are attested and validated against the request, but do not independently prove what it rendered. The legacy path also accepts an evidence ID mentioned in the summary as review membership for compatibility, which is not semantic proof of a useful review. Empty additive request and response fields are omitted from serialization so older digests remain stable. This accounting has focused CPU coverage; [Current state](CURRENT_STATE.md) tracks actual-model qualification.
   Response v6 can attach up to four typed noncausal observation references to one prior rival. A same-ID statement change through this route needs a newly reviewed, current-case source that survived the fitted request and an exact frozen prior digest. The same custody permits fresh references while preserving the statement byte for byte; formatting an already prefixed statement does not manufacture a change. Old references, causal citation classifications and predictions remain; separately verified unavailable observations may extend missing evidence, and the suggested next probe may change. New per-rival references exclude source-verified unavailable observations, without narrowing the legacy global review dispositions. The accepted asynchronous response commits an immutable prior/new hash and source-request link with the checkpoint. Storage rereads the applied response, prior row and frozen source set; an old reference cannot later be silently promoted to causal support. References remain advisory context with their disposition, never supporting evidence. Empty fields leave legacy serialization unchanged, and older records remain readable. Focused CPU and in-process tests cover this path; [Current state](CURRENT_STATE.md) tracks actual-model qualification.
   A mixed proposal that adds causal support alongside a valid noncausal reference may preserve only the reference. This narrow projection requires the exact frozen and visible prior, newly reviewed available current-case sources, preserved ordered old support with no duplicate or cross-classification, and unchanged contradiction, missing and prediction fields. It builds the saved rival from the prior row plus references, keeping its wording, status and requested probes unchanged; normal advisory status normalization is not bypassed. Storage independently binds the applied response and read-set and requires exact prior-plus-reference equality in the same transaction. A partial-rejection warning and immutable lineage distinguish this from accepting the proposed rewrite. Un-custodied extra support, unavailable/foreign references and changes to old evidence classes fail closed.
   The 48-record retrieval packet and 12-context deep brief reserve the bound task, honor explicit pending requests, and rotate cited evidence across live rival hypotheses before older source selections. The packet also keeps one newly selected fast source ahead of pending requests so a selected retrieval remains deliverable. This keeps a prior cited rival and its later counterevidence available for a second reasoning turn when they fit the existing bounds. Overflow, unavailable evidence, and prompt-fit loss remain explicit; the retained prediction is advisory, and an unregistered fact name is not a verified discriminating observation.
   A bounded hypothesis transition checks cited IDs against typed stored observations owned by the current case or its durable historical case links before carrying rivals across deep turns. For a new claim about one exact HTTP request, `claim_window_evidence_id` is a focused, source-custodied scope reference rather than causal support. A request-shaped contradiction must match that source's persisted target, action and exact request start/end; missing, malformed, different, or unscoped request windows cannot contest it. Same-ID updates cannot silently change the scope. Legacy unscoped saved rivals remain readable, without retroactive temporal certification. A later response that omits an old rival does not silently delete it, even when its historical excerpt leaves the compact request. Contradictions and coordinator-stamped prediction times survive compatible updates; unavailable citations, request-view gaps, conflicting same-ID rewrites, and capacity omissions remain explicit. This preserves advisory alternatives, not causal support or validation of model prose.
   Checkpoint v8 retains the summary source and, for an accepted advisory, the case evidence generation it reviewed. Case readback reports `current` only when that generation equals the latest case generation, `stale` when it is older, and `unknown` for legacy or non-advisory summaries without a frozen basis. A generation match is not proof that the fitted request contained every observation or that the summary is correct.
   The coordinator resolves typed hypothesis probe IDs and explicit requests only against current case capabilities, then passes any proposed follow-up through its existing manifest, permission, dependency, budget, and slot gate. Unregistered, unavailable, ambiguous, unauthorized, and exhausted needs remain labeled gaps. Deep context assembly prioritizes cited rivals, counterevidence, and pending detail references within a bounded model view. It reports required references that were omitted, unavailable, or quality limited; model-view trimming does not change retained observation records. The downstream Ollama fit defers uncited details first and fails closed if protected cited evidence cannot fit; it cannot silently discard that evidence or a rival hypothesis. Accepted exact detail requests remain in a bounded 16-item pending queue; overflow keeps the newest requests and reports the omitted older count. Source capture caps can still leave facts never retained, and those gaps cannot support a complete-coverage claim.
5. A separately approved repair executor, if qualified in the future, checks exact target and preconditions, journals the action, and verifies the affected task after the change. The current application does not expose automatic repair.

Steps 2–4 describe the **target primary loop**. The desktop candidate executes a narrower real Laya–Sol path for the exact local HTTP health task: one product GET, a source-bound listener check, and a Sol review of the resulting evidence. It also admits exact-name process presence and CPU-use questions through existing read-only collectors, but these establish sampled-time state rather than the cause of an earlier user problem. Other problem families have partial mixed-frontier machinery but no equally qualified affected-task outcome path. Some mixed decisions remain synchronous; the keyword planner still makes several basic decisions in model runs. At `12990ad`, finite mixed candidates, audit-bound deep-origin receipts and bounded terminal review were built and exercised in synthetic actual-model cases. The explicit hypothesis retirement path and summary freshness readback are built and tested in CPU/in-process cases; their behavior with actual model retirement intents and real Windows faults remains unqualified. Neither custody nor a fresh summary generation establishes a supported diagnosis.

## Separate graphs

- The **executable work graph** is an acyclic dependency/resource schedule. It says when registered read-only work may run, not what caused the fault.
- The **case evidence graph** contains temporal, provenance-backed relationships observed or carefully projected from this machine. Traversal and retrieval are bounded. An edge is not a diagnosis.
- The **reference graph** contains sourced, conditional IT mechanisms, distinguishing questions, and counterevidence. It may guide investigation but never supplies a missing machine observation. Category/diversity ranking is not a dependency graph.

## Authority and failure boundaries

All model requests are bounded, redacted, versioned, and tied to a case/state/deadline and registered capabilities. Responses are advisory and validated against the catalog; providers cannot specify arbitrary commands, executables, files, registry paths, URLs, queries, or permission tokens. Probe workers have deadlines, output limits, cancellation, and isolation where hard termination is needed. Coverage gaps, errors, timeouts, stale results, and contradictions are retained as data; they do not silently become healthy values.

Model residency and routing belong behind replaceable provider interfaces. The desired local primary profile keeps the fast brain warm while the deep brain works; sequential swapping is an explicit low-memory fallback, not the primary architecture. A resource lease must cover actual processes and measured RAM/VRAM, and model IDs must be verified at runtime. The opt-in `CodexReasoningProvider` uses the same fitted evidence/response validation as Ollama through `StructuredReasoningProvider`. Its installed Codex app-server must acknowledge GPT-6 Sol/OpenAI, report ChatGPT authentication, accept an ephemeral thread with no environment access, and report all inherited MCP servers disabled before evidence is sent. Custom provider/URL overrides fail closed; credentials stay with Codex and no paid API fallback is configured. A suspended Windows Job owns the server and descendants; cancellation, deadlines and bounded protocol/output checks precede result admission. The recorded model identity is the app-server acknowledgement, not independent server-side attestation. Production cloud deployment still requires minimization/export consent and qualification. The loopback application and MCP transport call the same case service; neither owns policy or storage.

Untrusted symptoms, logs, documents, and model text cannot cross the authority boundary. Structured redaction is defense in depth, not a guarantee of no novel secrets. A same-user or administrator compromise and faulty Windows providers remain residual risks. Never infer a healthy device from absent telemetry, or a repair from an unverified action.

The desktop exposes an explicit subscription mode while retaining deterministic default routing. Follow-up review membership checks detect omitted focused IDs; they do not establish meaningful evidence use, causal correctness, or task/target/time equivalence. Those remain separate acceptance questions. The exact local HTTP task path adds source-bound observation and narrower closure checks, but independent fixture restoration and case-result review remain necessary for qualification.

## Native-selected JSON boundary and approved copy

The native parent alone grants a selected file through its inherited private
pipe. The renderer cannot supply a path to the investigator; no HTTP or model
action exposes capture or copy execution. A bounded helper reads an immutable
local file capture using native identity and no-follow component traversal.
The parser task, UTF-8 check and JSON check share that capture and persist only
metadata. A full parser result covers decoding, so another identical-byte check
is unnecessary while its frozen Sol review is pending.

The optional copy executor is a separate authority. It accepts only removal of
a leading UTF-8 BOM whose remaining bytes already pass strict parsing. A
five-minute token binds that capture and an exact native-selected destination;
a second native confirmation authorizes execution. Schema 39 commits a
`json_copy_operations` claim before launching a fixed hidden helper. Native
create-only handles refuse overwrite and retain ancestor handles during the
write. A fresh read validates output identity, hash, size and strict parsing.
The terminal observation and receipt are immutable and kept separate from
read-only probe execution records. Restart converts pending claims to uncertain
and cannot restore write authority. No automatic retry, arbitrary transformation,
original-file repair, shell or application-recovery claim is permitted.
